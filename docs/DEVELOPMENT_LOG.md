# 开发日志

## 2026-11-17

### Phase 0 — 环境与可行性

- 环境巡检：Node 22.22.2 / npm 10.9.7 / MSVC 14.50 + Windows SDK 26100 / WebView2 148 都在，
  **唯独没有 Rust**。
- 安装 rustup 1.100.0（minimal profile，x86_64-pc-windows-msvc），验证 MSVC 链接可用。
- 起项目骨架：不用模板，不用打包器。
  - `package.json` 只有一个 devDependency（`@tauri-apps/cli`）。
  - `tauri.conf.json`：`devUrl` 指向 `scripts/dev-server.mjs`（自带 http 服务，零依赖），
    生产走 `frontendDist: ../src`。
  - `withGlobalTauri: true`，前端用 `window.__TAURI__` 直接调命令/订阅事件。
- 写 `overlay.rs`：透明窗口按 `SPI_GETWORKAREA` 摆位、置顶、跳任务栏、默认穿透。
- 写 `techcheck.rs`：12 项自检，全部用系统 API 回读，不用"应该可以"。
- 写 `win32.rs`：手写 12 个 Win32 声明（窗口矩形、工作区、`WindowFromPoint`、`GetPixel`、
  DPI、ExStyle），**没有引入 windows-sys**。
- 图标用 `scripts/make-icon.py`（Pillow）画一只 `><(((o>`，再 `tauri icons` 生成全套。

踩坑与决策：

1. **从命令里建窗口死锁。** 命令里直接 `ensure_overlay()` 会卡住不返回；
   套进 `run_on_main_thread` 也一样（`build()` 内部投递并等待事件循环，等于等自己）。
   改为在工作线程里发起创建。已在代码和架构文档里写清楚原因。
2. **隐藏 ≠ 停止。** 透明层 `hide()` 后仍留着一个 renderer 空转（+4% CPU / 70MB）。
   改成 `destroy()`，并给 `overlay.js` 加了 `visibilitychange` 停帧。
3. **`GetWindowRect` 比视觉窗口大 ~7px**（不可见边框），像素比对必须按内容区裁剪，
   否则会把桌面背景的变化算进差分。

### Phase 1 — 基础鱼缸

- 结构按任务书的模块划分：`simulation` / `fish` / `fish-behavior` / `aquarium` /
  `bubbles` / `seaweed` / `settings` / `main`。`coordinates.js` 留到 Phase 3 再建
  （现在没有真实用途，不写死代码）。
- 运动引擎：单一 rAF 循环 + 时间差推进 + 帧预算跳帧；暂停/隐藏直接停循环。
- 鱼的行为：游荡目标（每 0.8–5.4s 重掷）+ 避墙力 + 邻鱼排斥，用**转向速率上限**混合，
  所以没有瞬变；硬边界只做兜底。
- 首版截图发现两个问题，都当场改掉：
  1. 海草像"大头针"——直的茎 + 游离的 `╱`。改成"高度平方的弯曲 + 局部斜率选字"，
     并按簇分布（0.085 / 0.33 / 0.625 / 0.885），不再是一条栅栏。
  2. 两条鱼会叠字。排斥半径 46 → 62，权重 1.7 → 2.4。
- 设置面板做了最小可用集：海草 / 气泡 / 高帧率 60 / 透明层自检。
- 性能：`ctx.font` 只在变化时赋值；默认目标改 30fps（任务书的目标值），
  失焦降到 24fps，60fps 变成需要手动打开的选项。
  实测 30fps 单核 11.9%、60fps 17.4%、暂停 0%。

### Phase 2 — 桌面透明悬浮层

结构变化：

- `coordinates.js`：桌面坐标空间、颜色混合、矩形几何。鱼在缸里用缸内坐标（跟着窗口走），
  出了边界换成桌面坐标（留在屏幕上），越界/回缸各转换一次。
- `desktop-overlay.js`：鱼缸这一侧的桌面层控制器（创建/销毁/握手/推帧/捞鱼开关），
  与桌面层的通信只在这里发生。
- `overlay.js` 重写：不再自己造鱼，只收 `tank-frame` 快照并画；有变化才重绘。
- `simulation.js` 扩成"一个世界两个空间"：`boundary` 开关、`decide()`（越界/回缸意图）、
  `resolve()`（换空间）、`snapshot()`（喂桌面层）。
- `fish.js` 增加 `space` / `state` / `colorMix` / `goal`，`update()` 在世界对象里拿
  `hardBounds`（边界打开时关掉硬夹取，鱼才出得去）。

关键决策：

1. **单一大脑。** 桌面层不持有鱼，只画。这样"不瞬移/不重复/不消失"是模型自带的性质，
   不靠跨窗口同步去兜。
2. **交界处一帧切换画布。** 缸内鱼由鱼缸画、缸外鱼由桌面层画；越界那一帧 `colorMix=0`
   （还是墨黑），所以换画布这件事看不出来。
3. **销毁而不是隐藏桌面层。** 沿用 Phase 0 的结论；再次打开时用"ping/pong 握手"确认页面
   真的在听，握手完成前不发放外游意图（避免鱼游进一块还没准备好的玻璃）。
4. **捞鱼模式按距离动态切穿透。** 不是整屏接管：每 55ms 问一次光标，只有靠近鱼才可命中。
5. **回程加速。** 有目标时速度 ×1.7、加速度 ×1.6，往返从 19 秒缩到 7 秒，仍然是连续游动。

踩坑：

1. **`overlay_show` 同步命令把事件循环等死。** Phase 0 的坑又踩了一次——新写的命令没有
   照抄"在工作线程建窗口"的结论。改成 async + `spawn_blocking`，并在 `overlay.rs` 注释里钉死。
2. **快照漏字段。** `sim.snapshot()` 只发了 `id/x/y/facing/mix/color`，没发字形；
   桌面层 `fillText(undefined)`，于是"鱼出来了但看不见"（计数还是 3）。
   加 `g: fish.glyph` 后立刻正常。教训：跨窗口传的东西，用日志把真实内容打出来看。
3. **两个鱼缸。** 测试时旧进程没杀，同时跑了两个实例——屏幕上两套鱼。
   产品侧补了单实例 mutex（第二个实例把已有窗口提到前台后退出）。
4. **回缸 19 秒。** 远处的鱼按原速游回来太久，按钮长时间禁用。加 `hurry`。

调试手段：加了一个 `debug_log` 命令（写 `%TEMP%\text-aquarium-debug.log`），
前端在关键路径打一行。这比猜 console 快得多。稳定后周期性的心跳日志已删除，
只保留失败分支的调用。

### 交付前的整链路冒烟测试（`scripts/p2smoke.py`）

Phase 2 之前是逐项点出来的，重跑一次就得重新拼。补了一个可重复的整链路脚本：
启动 → 找到窗口 → 点「打开边界」→ 校验透明层几何 → 等鱼出缸 → 暂停 → 点「捞鱼」→
`WindowFromPoint` 三态判定 → 关边界 → 校验透明层已销毁。25 项，全绿才返回 0。

做这个脚本本身踩的坑（都不是产品 bug，是"测量方式"的坑，值得记下来）：

1. **坐标不能猜。** 窗口有原生标题栏，`GetWindowRect` 又比视觉窗口大 11px。
   一开始把屏幕上的长横线当成鱼缸边框——结果抓到的是浏览器里的线。
   改成 `GetClientRect + ClientToScreen` 拿客户区原点，在客户区里找"最长的连续墨线"，
   再把换算出来的 scale 和配置里的 760 CSS px 对账（1.750）。从此不依赖窗口摆在哪。
2. **空列表不等于静止。** 鱼在缸边淡出时检测不到，两帧都空就被当成"暂停生效"，
   于是根本没点暂停，后面瞄的是一个还在游的目标。改成：空列表返回"不知道"，
   要同一批位置前后一致才算停住。
3. **点完「捞鱼」光标还停在按钮上。** 断言却去看鱼身上那个点——永远不会命中。
   改成每次尝试先把光标放回鱼身上再判定。这一条害我以为产品坏了三次。
4. **穿透状态会影响点自家按钮。** 捞鱼模式下光标刚离开鱼，透明层还吃着鼠标，
   这一瞬间点鱼缸按钮会落空。所以点按钮前先移过去、等一个轮询周期（55ms），
   确认 `WindowFromPoint` 已经回到鱼缸再点。
5. **桌面不是真空。** 期间用户在用机器，前台窗口一会是浏览器一会是编辑器，
   截图里根本没有鱼缸。加了"窗口确实在最前"的前置判定，不满足就整轮作废（退出码 2），
   而不是拿别人的界面当鱼缸去断言。
6. **`cargo build` 和 `tauri build` 不是一件事。** 直接 `cargo build` 出来的是 dev 版 exe，
   它去连 `devUrl`（127.0.0.1:5183），dev server 没起来就是一块黑窗口（页面没加载，
   连按钮都测不到）。交付和测试一律用 `npx tauri build --debug --no-bundle`。

三次连跑：25/25、25/25、25/25。

### Phase 3 — 鱼缸与桌面之间的自由切换

Phase 2 已经能开关边界，但鱼的运动读起来像"漂"，不像"游"。这一阶段先把这件事解决，
再把坐标、状态、颜色的边角补齐。

**运动模型：从"随机转向"改成"游向某个地方"**

旧模型每隔一两秒给 heading 加一个随机角度。角度随机游走 = 布朗运动 = 看起来没有目的。
新模型每条鱼维护一个 `cruise` 目标点（离自己至少 240px，或鱼缸 40% 宽），朝它游；
到达（<34px）或超时（每条鱼 0.8–5.4s）才换一个。heading 仍然受 `turnRate` 限制，
所以转弯永远平滑；`Math.sin(pitch)` 直接来自 heading，头自然朝着行进方向。

**字形布局：一条线段转不了，但可以弯**

`src/js/glyph.js` 把一串字符拆成逐字符的 `(dx, dy)`：

```
u    = i / (n-1)                       0 = 头，1 = 尾
wave = sin(phase - u*3.1) * amp * (0.25 + 0.75u)
tilt = sin(heading) * 3.2 * (0.5 - u) * 2
dy   = wave + tilt
```

尾部摆幅是头的四倍，所以头几乎不动、身体在扭——和真鱼一样。`phase` 按
`bobSpeed*1.6 + speed*0.05` 推进，快鱼摆得快。俯仰让头在向下游时低于尾巴，
这是"头朝哪就游向哪"最直接的视觉证据。两个画布用同一份布局，所以穿边界时形状不变。

**这一阶段抓到的 bug（都不是猜出来的）**

1. **字体缓存和画布重置不同步。** `resize()` 里给 `canvas.width` 赋值会重置上下文的
   全部状态，包括 `ctx.font`，但渲染器缓存的 `currentFont` 还写着"已经设过 15px"。
   结果：字形按 8.79px 排布、却用 10px 的字画出来——一条鱼看起来像被拉开的项链。
   这是改成逐字符渲染后才暴露的。在 `resize()` 里清空缓存。
2. **`Infinity < 34` 是 false。** cruise 为 null 时 `toTarget` 是 Infinity，条件不成立，
   于是既不去选目标、又在下一行读 `this.cruise.x`——空指针。`node scripts/simtest.mjs`
   第一次跑就崩在这里。判断里显式加上 `this.cruise === null`。
3. **pitch 用的是转弯前的 heading。** 每帧先算 pitch 再转向，肉眼看是鱼身比运动方向
   慢半拍。改成转向之后再取。simtest 断言 `pitch === sin(heading)` 抓到的。
4. **被遮挡就停摆。** Chromium 认为窗口没人看得见时会节流 `requestAnimationFrame`。
   鱼缸被浏览器最大化挡住时，桌面上的鱼会一起僵住——因为模拟跑在鱼缸窗口里。
   两个窗口都加 `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding`。
   这是设计缺陷，不是性能优化。

**坐标加固**

- 回缸目标先算"缸内离鱼最近的点"，再钳到桌面内（±24px）。缸挂在屏幕边缘时，
  鱼不会被引到屏幕外。
- 如果钳制之后目标根本进不去（缸几乎完全出屏），鱼会在目标附近停住。给它 2.5s，
  还进不去就 `rescue()`：直接放回缸内中心附近。这一跳只可能发生在缸本身看不见的时候，
  用户看不到，但避免了"回缸永不完成 → 透明层永不关闭"的死状态。
- 拖动窗口/改窗口大小时 `onMoved`/`onResized` 触发重新测量；回缸中的鱼每帧重算目标，
  所以把缸拖到鱼身上时鱼会立刻进缸。

**连续切换**

回缸过程中，按钮不再是禁用的"回缸中…"，而是"重新打开"——点了就取消回缸
（`openBoundary()` 会把 returning 的鱼改回 outside）。人想反悔时第一反应就是再点一次，
禁用按钮只会让人以为程序卡住了。

**颜色**

淡入仍是 1.8/s。淡出改成按"离缸边的距离"连续映射：32px 内为 0，142px 外为 1，
中间用 smoothstep。原来的二值阈值（96px）会在鱼横穿那条线时闪一下。

### Phase 4 — 捞鱼交互、稳定性与性能

**拖动链路：只传意图，不传结果**

```
overlay: pointerdown → 命中鱼 → emit overlay-grab
tank:    grabFish(id) → state = "dragging"
overlay: pointermove → 本地画在指针处（不等 30Hz 快照）→ 每 16ms emit overlay-drag
tank:    dragFish(id, x, y) → 位置、朝向（拖动方向）
overlay: pointerup → emit overlay-drop（桌面坐标）
tank:    dropFish(id, x, y) → 落在缸内 enterTank（立即变黑）；落在桌面 → outside，18s 内不再自己往回游
```

桌面层的拖动是本地即时绘制的：等 30Hz 快照回来再画会有"拖影"，而鱼的权威位置仍在
tank 里。松手后两边在下一帧对齐。

兜底：2.5s 没收到拖动事件（层被销毁、鼠标丢了、程序被挂起）就把鱼放下，
不会把它冻在半空。拖动期间光标轮询始终让层保持可命中，松手立刻回到"靠近鱼才接住"。

**性能：先量，再改**

一开始想把"鱼缸重绘"干掉，结果测下来不是瓶颈。最后做的四件事：

1. 水草/气泡/砂砾画到离屏画布，14Hz 刷新（100 个字形 30Hz 重画没有必要）。
2. 鱼用脏矩形：只擦上一帧鱼所占的方框，再从离屏背景把那块补回来。全画布 clear + blit
   是这一层最贵的事。
3. 桌面层只清/画有墨的矩形（之前是全屏 clear）。
4. 没有鱼在桌面上时根本不发帧（之前 30Hz 发空数组），桌面层的 rAF 也随之停掉。

实测（锁屏 + 机器上有别的负载，`python scripts/perf.py`）：

| 模式 | CPU（单核占比） | 内存 | 进程 |
|---|---|---|---|
| 鱼缸模式 | 16.1% | 375 MB | 7 |
| 桌面模式（1 鱼在外） | 38.8% | 476 MB | 8 |
| 暂停（循环完全停止） | 5.3% | 386 MB | 7 |

暂停的 5.3% 是这套架构的地板价：一个 WebView2 窗口即使什么都不画，也要被 DWM 合成。
也就是说"画三条鱼"大约值 11% 单核，第二个透明全屏窗口再值 20% 左右。
进一步压缩只能换渲染方案（比如单窗口 + WS_EX_LAYERED 直接画），那是另一个工程，
不在这一版的范围里；数字如实记在 TEST_REPORT 第 29 节。

### Phase 5 — 打包与交付

**设置落盘**

`%APPDATA%\TextAquarium\settings.json`（Rust 写，先写 `.tmp` 再 rename，避免写一半）。
前端 `loadSettings()` 变成异步：优先读文件，读不到退回 localStorage；`saveSettings()`
两边都写（localStorage 给浏览器预览兜底）。卸载重装后设置还在。

**安装包**

NSIS，`installMode: currentUser`——不需要管理员权限，实际装到
`%LOCALAPPDATA%\Text Aquarium`（不是 `Programs` 子目录，构建前我以为会是，
写测试时特意改成从注册表的卸载项反查安装位置，而不是硬编码路径）。
产物：`src-tauri/target/release/bundle/nsis/Text Aquarium_1.0.0_x64-setup.exe`，
1.1 MB；解出来的程序本体 3.1 MB，前端资源全嵌在 exe 里，不再依赖 devUrl。

打包时踩到一个和代码无关的坑：`tauri build --bundles nsis` 要现场下载 NSIS 3.13 和
`nsis_tauri_utils.dll`，这台机器直连 GitHub 被代理挡掉（TLS 被掐断，报
`peer closed connection without sending TLS close_notify`），编译成功、打包失败。
改用官方的 `TAURI_BUNDLER_TOOLS_GITHUB_MIRROR` 指向镜像后一次过，镜像包仍然校验内嵌
SHA-1。这条写进 README 了。

**验收**

**长跑**

第一版 `soak.py` 用"首尾差值 > 25 MB 就算不稳"判定，结果 6 分钟报了 +64 MB 不稳定。
分进程、分阶段复测后发现那是预热：一个 WebView2 窗口的合成层是懒分配的，前 1.5 分钟
涨 15 MB 然后走平；透明全屏那一层涨到第 4 分钟才平。于是 soak 改成"先预热 3 分钟，
再量斜率"，判据换成 MB/min。结论与数字见 TEST_REPORT 第 29 节。

**关于那次"进程消失"**

一套 soak 跑到 15.6 分钟时进程树整体没了，页面也不再应答。查了应用事件日志、
CrashDumps、代码里的 `exit` / `close`，都没有痕迹；反过来做对照——只启动、开一次边界、
之后 20 分钟不碰它——进程好好活着。结论是测试脚本之间互杀（每个脚本都以
`taskkill /F /IM text-aquarium.exe` 开头结尾，两套并行就会互相打断）。
`soak.py` 现在遇到这种情况会直接说"the app disappeared after N min"并去事件日志求证。
