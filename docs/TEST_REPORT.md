## 8. 资源占用（本机 24 线程 / 2560×1600 / 175%）

| 场景 | 单核 CPU | 进程数 | 合计内存 |
|---|---|---|---|
| 默认 30 fps（前台） | 11.9% | 7 | 364 MB |
| 高帧率 60 fps | 17.4% | 7 | 366 MB |
| 暂停 | ≈ 0% | 7 | 364 MB |
| 自检期间（多一个透明层） | +约 4% | 8 | — |

拆分（30fps）：Rust 进程 0%、WebView2 浏览器进程 1.4%、GPU 进程 5.8%、renderer 4.7%。
24 线程机器上 11.9% 单核 ≈ 整机 0.5%。
内存的大头是 WebView2 自身的三个子进程，属 Tauri 基线成本。

未观察到内存随时间增长（20 分钟内 `WorkingSet` 稳定在 33–35 MB / 122 MB 两档）。

## 12. 这一阶段做了什么

| 交付项 | 实现 |

## 15. 不挡鼠标（核心验收项）

用 `WindowFromPoint`（Windows 自己用来决定谁接收点击的函数）判断：

| 场景 | 光标位置 | 命中窗口 | 结论 |
|---|---|---|---|
| 捞鱼关闭 | 小鱼正上方 | `WorkBuddy` / `Text Aquarium`（下层程序） | 点击穿透 ✔ |
| 捞鱼关闭 | 屏幕任意点 | 下层程序 | 点击穿透 ✔ |
| 捞鱼开启 | 光标移到小鱼上 | `Text Aquarium Overlay` | 只有鱼能接住点击 ✔ |
| 捞鱼开启 | 光标移到别处（等 0.4s） | 下层程序 | 自动恢复穿透 ✔ |

实现方式：捞鱼模式下每 55ms 问一次系统光标位置，只有光标落在字形框 14px 内
才把窗口切成可命中，其余时间一律穿透。所以**整屏不会长期被拦截**。

已知代价：光标离开小鱼后最迟 55ms 才恢复穿透；在这段时间里点空白处，
点击会被桌面层吃掉（代码里立刻恢复穿透，但这一次点击还是丢了）。

## 20. 资源占用（边界开启，两条 webview）

10 秒采样，按进程类型拆分：

| 进程 | 单核 CPU | 内存 |
|---|---|---|
| app（主进程） | 7.50% | 38.8 MB |
| app（webview host） | 6.56% | 133.9 MB |
| gpu-process | 7.97% | 87.2 MB |
| renderer（鱼缸） | 8.28% | 81.8 MB |
| renderer（桌面层） | 5.47% | 61.2 MB |
| utility ×2 + crashpad | 1.41% | 78.9 MB |
| **合计** | **37.2% 单核** | **约 482 MB** |

对照 Phase 1（只有鱼缸）：11.9% 单核 / 364 MB。
也就是说"桌面海洋"模式的增量约为 **+25% 单核 / +118 MB**，
主要来自第二个 renderer 和 GPU 进程对全屏透明窗口的合成。

24 线程机器上 37.2% 单核 ≈ 整机 1.6%。关闭边界后桌面层被销毁，
进程数回到 7，占用回到 Phase 1 基线。

> 这是本阶段最不理想的一项，记入 Phase 4 的优化清单：
> 降低桌面层重绘频率、只在鱼所在区域更新、空闲时合并两层的帧。

## 22. 本阶段发现并修掉的问题

| 问题 | 现象 | 根因 | 处理 |
|---|---|---|---|
| 点边界后卡在「正在打开桌面…」 | 状态永不推进，没有透明层 | `overlay_show` 是同步命令，在主线程里 `WebviewWindowBuilder::build()` 自己等自己 | 改成 async 命令 + `spawn_blocking`，窗口在工作线程创建 |

| 光标离开鱼后仍会吃掉一次点击 | 55ms 窗口内点空白无效 | 轮询做不到瞬时 | 点空白处立刻恢复穿透；记为已知代价 |

## 29. 性能实测

`python scripts/perf.py`，统计整棵进程树（主进程 + WebView2 子进程），
CPU 按"单个核心的百分比"计。测量时机器处于锁屏且后台有别的负载，绝对值偏高，
但同一次运行内的对比是可靠的：

| 模式 | CPU | 内存 | 进程数 | fps |
|---|---|---|---|---|
| 鱼缸模式（边界关闭） | 16.1% | 375 MB | 7 | 28 |
| 桌面模式（1 条鱼在外） | 38.8% | 476 MB | 8 | 24 |
| 暂停（循环完全停止） | 5.3% | 386 MB | 7 | — |

读法：**暂停时的 5.3% 是地板价**——一个 WebView2 窗口什么都不画，也要被 DWM
合成进桌面。也就是说"画三条鱼 + 水草"约值 11% 单核，多开一个全屏透明窗口再值 22%。
这一阶段把重绘压到了"只画变化的地方"，但没能改变这个结构：两个透明窗口就是两份合成成本。
要再降只能改渲染方案（单窗口 + `WS_EX_LAYERED` 直接画），超出本版范围。

长跑见下一小节——这一节先记一个教训：**用工作集判断泄漏会骗人**。

### 29.1 长跑：先分清"涨"是什么

第一版 `soak.py` 拿工作集的首尾差值判定，6 分钟就报 `+64 MB / NOT STABLE`。
把增长拆开看（每段 3 分钟，都从同一个冷启动状态开始）：

| 实验 | 做法 | 结果 |
|---|---|---|
| A 正常运行 | 收帧 + 绘制 | +13.1 MB/min |
| B 暂停 | 循环停掉，完全不收帧 | +3.1 MB/min |
| C 只收帧不绘制 | 把 `fillText` / `clearRect` 打空 | +2.8 MB/min |
| D 每帧整屏清除 | 补丁 `clearRect`，不用脏矩形 | 与 A 相同（+8.6 MB/min，曲线同形） |
| E 字形位置取整 | 补丁 `fillText`，去掉亚像素坐标 | 与 A 相同（+12.3 MB/min） |

C ≈ B 说明**收帧不涨内存**，涨的部分在"真的往画布上画"这条路上；D、E 说明
既不是脏矩形、也不是亚像素字形缓存（我原本最怀疑的那两个）。

再看单次采样的噪声：D 那一轮在 2.0 min 处工作集从 482 MB 直接掉回 445 MB，
然后又爬回 481 MB。这是 **Windows 在修剪工作集**（工作集 = 当前驻留的页，
可以随时被回收，Task Manager 默认显示的就是它）。所以工作集上升不等于泄漏。

判断泄漏要用 **commit（私有字节）**——它只在进程真的申请内存时上升，Windows 不会替你退。
`scripts/perf.py` 因此加了 `commit()`，`soak.py` 的判据也换成 commit 斜率。

### 29.2 换成 commit 之后

`python scripts/soak.py 20 --warmup 5`：边界开着、鱼来回跑，每 20 秒采一次，中途开关捞鱼和暂停。

| 阶段 | commit | 工作集 |
|---|---|---|
| 冷启动 | 310 MB | 470 MB |
| 预热 5 分钟后 | 349 MB | 510 MB |
| 再跑 15.6 分钟 | 361 MB | 524 MB |
| 斜率 | **+0.79 MB/min** | +0.9 MB/min |

鱼缸模式（不开边界）单独看更干净：375 → 392 MB 用 1.5 分钟，之后 4 分钟走平。

读法：**桌面模式冷启动会吃掉约 40 MB，之后是每分钟约 0.8 MB 的缓慢上台阶**
（V8 堆涨上去不还给系统、画布缓冲随覆盖面积增加）。按这个斜率挂一整天大约多 300–400 MB，
不影响使用，但也谈不上"零增长"。要继续压，先压桌面层画布（dpr 1.5 → 1 能省掉一半像素），
或者干脆换成单窗口 + `WS_EX_LAYERED`，而不是继续挤鱼缸那边。

### 29.3 一次没跑完的长跑

同一套 soak 在 15.6 分钟处，进程树整体消失（`0 proc`），页面不再应答。当时的表现是
`ws 524 MB / commit 361 MB`，不是内存耗尽。查了一圈：

| 查了什么 | 结果 |
|---|---|
| 应用事件日志（Application Error / WER） | 没有 `text-aquarium` 或 `msedgewebview2` 的崩溃记录 |
| `%LOCALAPPDATA%\CrashDumps` | 没有对应 dump |
| 代码里的 `process::exit` / `window.close` | 没有 |
| 对照实验：只启动 + 开一次边界，之后完全不干预 20 分钟 | 存活，20 分钟无异常 |

也就是"有人把它关了"而不是"它自己崩了"——最可能是测试脚本之间互相 `taskkill`（这些脚本
都以 `taskkill /F /IM text-aquarium.exe` 开头和结尾，两个脚本同时跑就会互杀，我自己就撞过两次）。
这一条写进 `soak.py`：进程消失时打印 "the app disappeared after N min" 并去事件日志求证，
而不是抛一个看不懂的 traceback。

| 4 | 关掉气泡会写文件 | `{"seaweed": true, "bubbles": false, "highFps": false}` |
| 5 | 内存状态同时更新 | `bubbles = false` |

写盘路径 `%APPDATA%\TextAquarium\settings.json`，Rust 端先写 `.tmp` 再 rename，

| 项目 | 结果 |
|---|---|
| 产物 | `src-tauri/target/release/bundle/nsis/Text Aquarium_1.0.0_x64-setup.exe` |

打包这一步在本机踩到一个和代码无关的坑：`tauri build --bundles nsis` 会去 GitHub
下载 NSIS 3.13 和 `nsis_tauri_utils.dll`，而这台机器直连 GitHub 不通（代理回 502），
表现为 `peer closed connection without sending TLS close_notify`。用官方的镜像变量解决：

```bash
TAURI_BUNDLER_TOOLS_GITHUB_MIRROR="https://ghfast.top/https://github.com/" \

```

这一点写进 README，免得下次构建以为是代码坏了。

### 35.2 躲闪的方向语义（simtest 断言）

- 迎面：朝向反转（cos(Δheading) < -0.5），往回逃——真实鱼类的 C 型惊跳。
- 背后：朝向不变、目标点沿原航向（夹角 < 25°），加速前冲。
- 参数：4.2× 速度、3.5× 加速度、0.4s、冷却 1.4s。

### 35.3 测试基础设施的教训

- p2smoke 旧"补点一次边界按钮"会在回缸途中**把边界重新打开**（RETURNING
  再点 = 重新打开，是产品特性）；改为"8s 内鱼群是否开始回家"判定点击生效。
- 取消暂停必须带效果验证（still() 检查鱼是否真的在动），否则边界按钮会
  以"暂停中"拒绝关门，整套测试白等 80 秒。
- 透明层首个点击可能要先交焦点：拖框手势加预热按住 + 中间步进。
- 像素计数有桶合并噪声（只会偏小）：取多次采样的最大值作基准。
